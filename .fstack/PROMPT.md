# Nakode coding instructions

- Treat Nakode as a server/API/SDK product, not a privileged TUI. First identify the owning server state and invariant, public command/query/watch shape, SDK behavior, and client projection.
- Server/domain behavior belongs in `src/server.rs`, `src/state.rs`, `src/runtime.rs`, providers, tools, persistence, or orchestration modules. Public behavior belongs in `proto/nakode/v1/nakode.proto`; reusable reconnect, retry, paging, hydration, and selection behavior belongs in `crates/nakode-sdk/`.
- Frontends issue typed SDK calls and render complete replacement snapshots. Do not call providers, persistence, tools, or orchestration from rendering/input code, and do not implement product behavior only in the TUI.
- Preserve stable IDs, monotonic revisions, idempotency keys, capability checks, paging limits, provider-qualified model attribution, bounded attributable delegation, cancellation, and explicit handoff semantics.
- Protobuf Rust output is generated by `crates/nakode-api/build.rs`; edit the schema or generator inputs, never generated output. Persistence changes require forward migration compatibility and coordinated fixtures/docs.
- FStack consumes only the public Nakode protocol. Never add FStack-specific direct database/provider behavior to Nakode or require a frontend to supervise Nakode processes.

Before completion run:

```sh
cargo fmt --all -- --check
cargo test --locked --all-targets --all-features
cargo clippy --locked --all-targets --all-features -- -D warnings
```

For TUI/control/rendering changes also run the committed headless scenario:

```sh
cargo run -- tui-eval --scenario tests/tui_scenarios/agent_smoke.jsonl
```
